# NEURA Strategy Prediction Service

A small FastAPI service with one job: given a student's most recent lesson
performance, predict which of NEURA's five teaching strategies to use next.

```
visual | textual | step-by-step | example-based | socratic
```

This is the **only** ML model in NEURA. It does not diagnose anything about
the learner (no ADHD/dyslexia/difficulty classification) — it only answers
"how should the next lesson be taught?". The existing LLM tutor
(`server/aiPrompts.ts`) still decides *what* to teach; this service decides
*how*.

## Dataset

Source: `ml/data/strategy_dataset.csv` (provided dataset, 19,630 rows).

Columns: `student_id, skill_id, previous_accuracy, response_time, attempts,
hints_requested, topic_mastery, previous_strategy, next_recommended_strategy`.

Full inspection report: `python -m src.inspect_dataset` (see below for the
key findings; re-run any time to regenerate on the current CSV).

| **Exact duplicate rows** | **11,964 (61%)** |
| Rows after dedup | 7,666 |

| Numeric ranges | previous_accuracy/topic_mastery ∈ [0,1]; response_time ∈ [1,180]s; attempts ∈ [1,15]; hints_requested ∈ [0,7] — no out-of-range or negative values found |

### Leakage & determinism investigation

The brief explicitly warns: *"If there are suspiciously high or perfect
metrics, do NOT simply claim that the model is perfect. Investigate."* Two
things came out of that investigation, and both are documented here rather
than hidden:

1. **Row duplication.** 61% of rows are exact duplicates of another row
   (11,964/19,630), and this holds even considering `student_id` — i.e. the
   same student's exact same observation appears many times. This looks like
   the dataset was balanced across the 5 target classes by duplicating
   existing rows rather than collecting new ones. We **drop exact duplicates
   before splitting** (`preprocessing.load_clean_dataset`), leaving 7,666
   unique observations — training on the duplicated version would let the
   model "solve" the problem by literally memorizing repeated rows.

2. **The target is (almost) a deterministic function of the features.**
   Grouping the deduplicated data by the full feature tuple
   `(previous_accuracy, response_time, attempts, hints_requested,
   topic_mastery, previous_strategy)`, **0 of 7,472 distinct combinations map
   to more than one target class** — every feature combination has exactly
   one associated label. This is true even dropping `previous_strategy` and
   using only the 5 numeric features (only 5 of 7,415 combinations are
   ambiguous). Concretely: `previous_strategy ∈ {example-based, socratic}`
   maps to `next_recommended_strategy = step-by-step` **100% of the time**;
   high `attempts`/`hints_requested` reliably map to `step-by-step`/`visual`;
   low `attempts`/`hints_requested` with low `topic_mastery` maps to
   `example-based`/`socratic`; etc. (see `ml/models/decision_tree_rules.txt`
   for the exact learned thresholds).

   **What this means:** this dataset appears to have been generated by a
   rule/formula, not sampled from noisy real student behavior. That's why
   Random Forest and Gradient Boosting both hit **100.00%** validation
   accuracy — not because the model is unusually good, but because the
   labeling function has no noise for a flexible model to fail to fit. A
   100% score here is a property of the data, not evidence of a correct
   real-world predictor, and should not be presented as one.

   **Practical consequence for model choice:** since every non-trivial model
   converges on ~100% validation performance, raw accuracy can't tell us
   which is "best" — so we picked the **simplest** model within a small
   tolerance of the top score (see "Model selection" below) instead of
   defaulting to the least explainable one.

## Model

### Features

Inputs (exactly the 6 the brief specifies):
`previous_accuracy, response_time, attempts, hints_requested, topic_mastery,
previous_strategy` (one-hot encoded). `student_id` and `skill_id` are **not**
used as predictive features — `student_id` would let the model key off
identity rather than learning state, and `skill_id` is treated as contextual
metadata only (report-worthy, not predictive) per the brief.

### Student-level split

Interactions belong to students who appear multiple times (mean 10.5
rows/student, up to 417 for one student), so a random row-level split would
leak a student's other rows across train/test. `preprocessing.student_level_split`
splits by `student_id` (70% train / 10% val / 20% test students) so no
student's rows appear in more than one split.

### Models compared

Majority-class baseline, Logistic Regression, Decision Tree, Random Forest,
Gradient Boosting — all on the identical student-level split, evaluated with
accuracy, macro-F1, weighted-F1, macro precision/recall, per-class F1, and a
confusion matrix (`src/evaluate.py`).

| Model | Val accuracy | Val macro-F1 |
|---|---|---|
| Majority baseline | 49.4% | 0.132 |
| Logistic Regression | 91.7% | 0.908 |
| **Decision Tree** | **99.4%** | **0.981** |
| Random Forest | 100.0% | 1.000 |
| Gradient Boosting | 100.0% | 1.000 |

### Model selection: Decision Tree

Per the brief ("prefer the model with reasonable performance and
simplicity") and given the determinism finding above, we select the
**simplest model within 2 points of the best validation macro-F1**, rather
than the ensemble that happens to score a flat 100%. That's the
**Decision Tree** (`max_depth=8, min_samples_leaf=10`).

Held-out test set (374 students, never seen during training or selection):

| Metric | Score |
|---|---|
| Accuracy | 98.64% |
| Macro F1 | 0.9575 |
| Weighted F1 | 0.9864 |
| Precision (macro) | 0.9691 |
| Recall (macro) | 0.9481 |

Per-class F1: visual 0.965, textual 1.000, step-by-step 0.840 (weakest —
step-by-step and visual are the two classes the tree occasionally confuses
at high attempts/hints values), example-based 0.998, socratic 0.982.

Full metrics (including the confusion matrix and validation numbers for
every candidate) are saved to `ml/models/metrics.json` after training. The
exact learned split rules are saved to `ml/models/decision_tree_rules.txt` —
short enough to walk through directly in a viva.

### Feature engineering & ablation studies

We systematically explored two extensions beyond the base 6-feature snapshot:

1. **Rolling historical averages over last 2–3 lessons (`rolling_acc_3`, `rolling_time_3`, `rolling_hints_3`)**:
   - Implemented via `preprocessing.add_rolling_features()` computed per-student with `min_periods=1`.
   - Results on held-out test set: Decision Tree Test Macro-F1: **0.9575** (identical to single-lesson snapshot); step-by-step F1: **0.8402**.
   - *Why*: Because the CSV dataset labels were generated strictly from single-observation snapshot rules, historical rolling features do not provide additional predictive signal for this synthetic labeling function.

2. **Categorical `skill_id` exploration**:
   - Evaluated `skill_id` (one-hot encoded categorical) alongside the numeric features.
   - Results on held-out test set: Decision Tree Test Macro-F1: **0.9575**; per-class F1s remained unchanged across all 5 strategies.
   - *Conclusion*: `skill_id` does not meaningfully improve per-class F1 (the underlying labeling rule does not vary by skill). Per the requirement, we do **not** add `skill_id` to the production inference payload, keeping the API lightweight and avoiding artificial overfitting.

### Model limitations & real-world validation

The training target in `strategy_dataset.csv` is `next_recommended_strategy` — i.e. whatever strategy
a prior heuristic/rule recommended for that learner state, not a ground truth measurement of "the objectively best strategy for this student."
Formally:

```
learner state  →  historical recommended strategy   (what this model learns)
learner state  →  objectively best strategy          (NOT what this model learns)
```

**Crucial caveat:** High validation/test accuracy metrics on this CSV reflect **formula reconstruction** rather than proof of pedagogical efficacy. Neither adding rolling averages nor categorical `skill_id` changes this fundamental limitation of the synthetic data.

To bridge this gap in production:
- The live application logs structured outcome telemetry (`[ML Live Outcome]` in `server/routers.ts`) recording `(strategyUsed -> actual subsequent accuracy/response_time/hints/attempts)` alongside the predicted recommendation.
- All live lesson interactions are persisted in MySQL via `lessonPerformanceEvents`.
- Once sufficient live student sessions are accumulated, NEURA can be validated and retrained on true empirical learning gains rather than synthetic labels.

## Cold start (onboarding)

A new student has no lesson history, so nothing is fabricated. Instead
(`client/src/components/AdaptiveBaselineQuiz.tsx`), a new student is walked
through one mini-task per strategy (all 5), and real performance
(`correct`, `timeTaken`, `attemptCount`, `hintUsed`) is recorded for each via
`adaptive.submitBaselineAssessment`.

**Initial strategy derivation** (`server/db.ts#calculateStrategyScore` +
`recordStrategyObservationsBatch`) is a simple, transparent scoring formula
— *not* a second ML model, per the brief:

```
score = 50 (correct) or 10 (incorrect)
      + time bonus:   +20 (≤15s, correct) / +5 (≤15s, incorrect)
                       +15 (≤35s, correct) / +0 (≤35s, incorrect)
                       +5  (>35s, correct)  / -5 (>35s, incorrect)
      + attempt bonus: +15 (1st attempt) / +5 (2nd attempt) / +0 (3rd+)
      + hint bonus:    +15 (no hint used) / +0 (hint used)
      clamped to [0, 100]
```

Each strategy's scores are averaged across the mini-tasks; the
highest-scoring strategy becomes `preferredStrategy`, persisted to
`studentStrategyProfiles` alongside all 5 strategies' scores
(`strategyScores`) and a confidence score. This is the "initial teaching
strategy" used for the student's first real lesson.

## Normal loop (after the first lesson)

```
previous strategy + last lesson's performance
        → POST /predict/strategy (this service)
        → next strategy
        → LLM tutor teaches the next lesson in that mode
        → performance recorded again
        → repeat
```

See the top-level integration notes for how the TypeScript backend calls
this service, persists each interaction, and falls back to the student's
last known strategy if this service is unavailable.

## API

### `GET /health`
```json
{"status": "ok"}
```

### `POST /predict/strategy`
Request:
```json
{
  "previous_accuracy": 0.72,
  "response_time": 15,
  "attempts": 2,
  "hints_requested": 1,
  "topic_mastery": 0.68,
  "previous_strategy": "visual"
}
```
Response:
```json
{"next_strategy": "example-based", "confidence": 0.81}
```
All fields are validated with Pydantic (`src/schemas.py`): `previous_accuracy`
and `topic_mastery` must be in `[0, 1]`, `response_time` must be `> 0`,
`attempts` must be `>= 1`, `hints_requested` must be `>= 0`, and
`previous_strategy` must be one of the 5 valid strategies. Invalid input
returns `422` with the specific validation error.

## Running it

```bash
cd ml
python3 -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt

# Inspect the dataset (optional, regenerates the report above)
python -m src.inspect_dataset

# Train (writes ml/models/strategy_model.joblib + metrics.json)
python -m src.train_strategy

# Run the service
uvicorn main:app --host 0.0.0.0 --port 8001

# Tests
pytest tests/ -v
```

The trained model artifact is committed to the repo (`ml/models/`) so the
service runs immediately after `pip install`; re-run `train_strategy.py` to
regenerate it from scratch.
